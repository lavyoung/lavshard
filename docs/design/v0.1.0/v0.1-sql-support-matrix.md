# LavShard v0.1 SQL 支持矩阵

## 1. 目的

本文定义 v0.1 可以执行、可以透传和必须拒绝的 SQL。实现、测试、README 和发布说明必须以本矩阵为准。

v0.1 的目标不是尽可能多地接受 SQL，而是保证已接受 SQL 一定能够在访问数据库前得到唯一、正确的物理路由。

## 2. 适用范围

- Java 17。
- Spring Boot + MyBatis。
- MySQL 方言。
- 每条 SQL 最多包含一个受 LavShard 管理的分片表。
- 使用一个非空等值分片键确定唯一逻辑桶和唯一物理节点。
- 目标拓扑覆盖仅分表、仅分库、分库 + 分表，三种形态使用同一 SQL 能力边界。
- 支持同一应用配置多张分片表。
- 支持单物理数据库本地事务，不支持分布式事务。
- 支持 MyBatis `ExecutorType.SIMPLE` 和 `REUSE`；`BATCH` 在 v0.1 拒绝。

## 3. SQL 分类

| 分类 | 条件 | 行为 |
| --- | --- | --- |
| `MANAGED` | 命中已配置分片表 | 严格执行解析、绑定、路由、改写和事务校验 |
| `PASSTHROUGH` | 位于 LavShard 集成范围内，但只访问明确普通表 | 不改写 SQL，路由到配置的默认数据源 |
| `OUT_OF_SCOPE` | Mapper 或 `SqlSessionFactory` 不由 LavShard 管理 | 完全绕过 LavShard |
| `UNSUPPORTED` | 命中分片表，但语法无法安全地产生唯一物理路由 | 执行前抛出 `UnsupportedSqlException` |

约束：

- 解析失败的受管 SQL 不能降级为 `PASSTHROUGH`。
- 分片表规则缺失或不完整不能降级到默认数据源。
- 同时出现分片表和普通表的 SQL 在 v0.1 视为 `UNSUPPORTED`。
- SQL 引用的表全部位于普通表允许列表时，保持原 SQL 并透传到默认数据源；普通表之间的 JOIN 由数据库原生处理。
- 未出现在分片规则或普通表允许列表中的表固定拒绝，不能根据“未找到规则”推断为普通表。
- 不引用表的只读 SQL（例如 `SELECT 1`）可以透传到默认数据源；连接会话和管理语句仍按第 8 节拒绝。
- 管理范围优先按 `SqlSessionFactory` 或 Mapper 包配置，不依赖方法命名猜测。

## 4. SELECT

| 场景 | v0.1 | 说明 |
| --- | --- | --- |
| 单表且 `shard_key = ?` | 支持 | 参数成功绑定且非空 |
| 单表且 `shard_key = literal` | 支持 | 字面量类型必须与规则兼容 |
| 分片键条件位于简单 `AND` 中 | 支持 | 其他条件不影响唯一路由 |
| 分片键位于 `OR` 中 | 拒绝 | v0.1 不做布尔表达式路由归约 |
| `IN`、`BETWEEN`、`>`、`<` | 拒绝 | 可能产生多路由或范围路由 |
| 无分片键 | 拒绝 | 不执行全路由扫描 |
| 分片键为 `NULL` | 拒绝 | 不定义空值所在分片 |
| 单个受管分片表使用别名 | 支持 | AST 必须正确识别限定列名 |
| JOIN | 拒绝 | 包括分片表与普通表 JOIN |
| 子查询、CTE、`UNION` | 拒绝 | 即使看似只命中一个分片也不猜测 |
| `ORDER BY`、`LIMIT` | 支持 | 仅在已经确定单分片后下推执行 |
| 聚合、`GROUP BY`、`HAVING` | 支持 | 仅在已经确定单分片后由数据库执行 |
| `SELECT ... FOR UPDATE` | 支持 | 必须位于已绑定同一物理数据库的本地事务中 |

## 5. INSERT

| 场景 | v0.1 | 说明 |
| --- | --- | --- |
| 单行 INSERT 且显式包含分片键 | 支持 | 分片键值必须可绑定且非空 |
| 单行 INSERT 使用 MyBatis 动态 SQL | 支持 | 必须保留 additional parameters |
| 数据库生成主键 | 支持 | 仅支持单行、单节点和 MyBatis 标准 KeyGenerator；只保证物理表内唯一 |
| 多行 INSERT，全部命中同一节点 | 拒绝 | v0.1 不拆分或重建多值参数；完成专项设计与测试后再开放 |
| 多行 INSERT，命中多个节点 | 拒绝 | 不拆分写入，不产生部分成功 |
| 缺少分片键或使用数据库默认值 | 拒绝 | 路由发生在 SQL 执行前 |
| 分片键为函数或数据库表达式 | 拒绝 | 无法在客户端稳定求值 |
| `INSERT ... SELECT` | 拒绝 | 涉及源表路由和结果搬运 |
| `ON DUPLICATE KEY UPDATE` | 拒绝 | 首版不承担唯一键和分片键更新组合语义 |

## 6. UPDATE

| 场景 | v0.1 | 说明 |
| --- | --- | --- |
| WHERE 中包含等值分片键 | 支持 | 唯一路由后由数据库处理其他条件 |
| SET 不修改分片键 | 支持 | 普通列更新 |
| SET 修改分片键 | 拒绝 | 修改分片键等价于跨分片数据迁移 |
| 无分片键 | 拒绝 | 不广播 UPDATE |
| JOIN UPDATE、多表 UPDATE | 拒绝 | 不支持多表路由 |
| 分片键条件为 `IN`、范围或 `OR` | 拒绝 | v0.1 不拆分写操作 |

## 7. DELETE

| 场景 | v0.1 | 说明 |
| --- | --- | --- |
| WHERE 中包含等值分片键 | 支持 | 唯一路由 |
| 无分片键 | 拒绝 | 不广播 DELETE |
| 多表 DELETE | 拒绝 | 不支持多表路由 |
| 分片键条件为 `IN`、范围或 `OR` | 拒绝 | v0.1 不拆分写操作 |

## 8. DDL 与其他语句

| 场景 | v0.1 | 说明 |
| --- | --- | --- |
| DDL | 拒绝 | 由 Flyway、Liquibase 或独立部署流程管理 |
| 存储过程、`CALL` | 拒绝 | 路由和副作用无法可靠分析 |
| `LOAD DATA`、文件导入 | 拒绝 | 由独立数据导入流程处理 |
| 显式事务控制 SQL | 拒绝 | 事务边界必须由 Spring/MyBatis 集成层管理 |
| `SET` 等连接会话语句 | 拒绝 | v0.1 不保证在正确物理连接上建立会话状态 |
| MySQL 管理语句 | 拒绝 | 不进入业务分片路由链路 |

## 9. 参数绑定约束

- 解析阶段只记录字面量或 JDBC 参数位置，不读取框架参数对象。
- MyBatis 适配器基于 `BoundSql.parameterMappings` 的有序列表绑定参数。
- 优先读取 `BoundSql` 的 additional parameters，再读取参数对象。
- 类型转换必须显式；不能通过 `toString()` 隐式兼容未知类型。
- 不支持的分片键类型抛出 `ParameterBindingException`。
- SQL 重写没有删除占位符时保留原始参数顺序；未来拆分 `IN` 时为每个 `RouteUnit` 生成参数投影。

## 10. MyBatis 缓存与执行顺序

必须遵循：

```text
获取原始 BoundSql
    ↓
解析、绑定、路由、改写
    ↓
构造物理 BoundSql / MappedStatement
    ↓
基于物理 SQL 创建 CacheKey，并追加 dataSourceId、ruleVersion、topologyVersion
    ↓
执行 Executor
```

禁止在 CacheKey 创建后才改写逻辑表名。即使物理表名相同，不同数据库也必须产生不同 CacheKey；规则或拓扑切换时必须清理不再兼容的二级缓存。普通表透传也必须使用默认数据源的稳定 ID 隔离缓存。

重建 MyBatis 对象时必须保留与本次 SQL 相关的：

- `ParameterMapping` 顺序。
- additional parameters。
- `KeyGenerator`、`keyProperties` 和 `keyColumns`。
- `ResultMap`、超时、fetch size、statement type 和缓存配置。

必须覆盖 Executor 的查询、游标和更新入口。v0.1 明确拒绝 `ExecutorType.BATCH`；完成批次级单节点约束、刷新时机、生成键和失败语义测试后再开放。

## 11. 事务约束

- 第一次受管 SQL 固定事务的 `dataSourceId`、`ruleVersion` 和 `topologyVersion`。
- 同一事务后续 SQL 必须与已固定状态兼容。
- 同一事务访问不同物理数据库立即失败。
- 同一事务可以访问同一物理数据库内的多个物理表，但每条 SQL 仍必须产生唯一安全路由，且规则、拓扑版本兼容。
- 普通表透传到不同于事务已绑定数据源的默认库时立即失败。
- `SELECT ... FOR UPDATE` 只能在单分片事务中执行。
- 发生解析、绑定、路由或执行异常后必须恢复非事务上下文；事务资源在事务完成回调中清理。

## 12. 验收清单

- 每个“支持”场景至少有一个成功集成测试。
- 每个“拒绝”场景验证数据库未收到 SQL。
- 每个“透传”场景验证 SQL 未被改写。
- POJO、Map、`@Param`、动态 SQL 和 additional parameters 均有测试。
- MyBatis 一级和二级缓存均验证不同物理表不会串读。
- 仅分表、仅分库、分库 + 分表分别完成真实 MySQL CRUD；仅分库和组合模式必须覆盖跨数据库同名物理表的缓存隔离。
- 生成键、事务回滚和异常清理均有测试；Batch 入口验证为执行前拒绝。
- MySQL 语法行为使用 Testcontainers 验证，不以 H2 代替。
