# LavShard 分片数据模型规范

## 1. 目的

分片路由只能保证 SQL 到达计算出的节点，不能自动保证分片键选择、唯一约束、关联关系和扩容方案正确。本文规定使用 LavShard 前必须完成的数据模型设计。

## 2. 分片键选择

合格的分片键应同时满足：

- 非空：每条受管记录创建时都能得到分片键。
- 不可变：记录生命周期内不修改分片键。
- 高基数：不同值足以分散到全部逻辑桶。
- 分布合理：不能长期集中于少量租户、日期或业务状态。
- 查询可得：核心查询入口天然携带分片键。
- 业务稳定：不会因组织合并、账号迁移等频繁变化。

候选键评估至少记录：

| 维度 | 问题 |
| --- | --- |
| 数据分布 | 最大租户或最大键值占总数据多少？ |
| 写入分布 | 是否会形成单桶热点？ |
| 查询覆盖 | 核心查询中携带该键的比例是多少？ |
| 关联局部性 | 需要事务和 JOIN 的数据是否使用相同键？ |
| 生命周期 | 键值是否可能被修改、合并或重新归属？ |
| 合规隔离 | 是否需要按租户、区域进行物理隔离？ |

不建议直接使用：

- 当前日期或单调时间作为简单取模输入。
- 状态、地区等低基数字段。
- 可以被用户修改的手机号、邮箱、用户名。
- 随业务组织关系频繁变化的部门 ID。

## 3. 主键与全局 ID

- MySQL 自增主键只能保证单个物理表内唯一。
- 如果 ID 会跨分片展示、引用或合并，必须由业务或独立 ID 生成器提供全局唯一 ID。
- LavShard v0.x 不内置 ID 生成器，避免把路由组件扩展成基础设施平台。
- ID 生成策略必须在写数据库前完成，不能依赖插入后才知道分片键。
- 如果主键同时作为分片键，算法必须明确支持其数据类型和规范化形式。

可选策略包括数据库号段、UUID/ULID、Snowflake 类算法或业务预分配；具体选择由吞吐、排序性、时钟风险和运维能力决定。

## 4. 唯一约束

物理数据库只能原生保证单个分片内的唯一性。

- 唯一索引包含分片键时，可以将冲突稳定路由到同一分片。
- 唯一索引不包含分片键时，不能宣称全局唯一。
- 需要全局唯一的邮箱、订单号等字段，应选择以下方案之一：
  - 由业务生成天然全局唯一值。
  - 建立集中式或独立分片的唯一键登记表。
  - 建立带一致性协议的全局 Lookup 索引。
  - 将唯一字段纳入分片键，但必须重新评估查询局部性。

LavShard v0.x 不自动维护全局唯一索引。应用必须明确接受失败语义和一致性成本。

## 5. 关联、外键与事务边界

- 禁止跨分片数据库外键。
- 需要同库事务和 JOIN 的表应采用相同分片键、相同 `bucketCount` 和兼容的桶到节点映射。
- 父子表的子记录应保存父表分片键，避免只通过子表主键查询而无法定位。
- 跨分片业务流程使用最终一致性、Saga/事件驱动或成熟分布式事务方案，不能伪装成本地事务。
- LavShard v0.x 事务内只允许访问一个物理数据库。

“同一节点”不等于“可以 JOIN”。字符集、排序规则、字段类型和表结构也必须兼容。

## 6. 查询访问路径

每张分片表上线前应列出主要查询：

| 查询 | 是否包含分片键 | 预计路由数 | 处理策略 |
| --- | --- | --- | --- |
| 按主业务键查询 | 是 | 1 | LavShard 单路由 |
| 按全局订单号查询 | 视模型而定 | 1 或未知 | 设计为分片键或外部 Lookup |
| 后台条件搜索 | 通常否 | 全部 | 搜索引擎、数仓或独立查询库 |
| 报表聚合 | 通常否 | 全部 | 离线数仓/OLAP，不走在线分片库 |

原则：

- 在线核心链路优先单路由。
- 不应以“以后支持广播查询”弥补错误的分片键设计。
- 高频二级查询优先使用专用索引、搜索系统或冗余读模型。
- 管理后台和报表不应无上限扫描所有生产分片。

## 7. 写入与分片键变更

- INSERT 必须在客户端得到完整分片键。
- v0.1 拒绝多行 INSERT；后续版本只有先计算全部目标并确认同一节点后才可开放。
- UPDATE 禁止修改分片键。
- 修改分片键必须转化为显式迁移：读取旧记录、在新分片插入、校验、删除旧记录，并处理并发写入。
- DELETE 必须携带可产生唯一路由的分片键。
- 幂等键和重试策略必须在分片级事务边界内成立。

## 8. 逻辑桶与物理节点

LavShard 使用固定逻辑桶隔离算法与物理拓扑：

```text
shardKey → logicalBucket → ShardNode → dataSource + physicalTable
```

约束：

- `bucketCount` 在建表前确定，已有数据后不能在线修改。
- `hashVersion` 是持久化协议，不得静默更换。
- 每个逻辑桶必须且只能映射到一个当前写节点。
- 每个物理节点使用稳定 `nodeId`，不能以配置列表下标作为身份。
- 拓扑变化产生新的 `topologyVersion`。
- 路由计划和诊断日志携带规则版本与拓扑版本。

逻辑桶数量需要在配置规模和未来扩容粒度间取平衡。初始默认值必须通过 ADR 决定，不在代码中散落魔法数字。

## 9. 热点与容量规划

上线前至少估算：

- 当前和三年预估总行数、数据大小。
- 单分片峰值 QPS/TPS。
- 最大租户、最大单键和最大日写入量。
- 索引大小与 Buffer Pool 命中率。
- 单表增长速度、归档周期和备份恢复时间。
- 扩容触发阈值和预留节点容量。

Hash 能改善大量独立键的整体分布，但不能消除单个超级租户或热点键。热点检测应基于逻辑桶和节点两个层级。

## 10. Schema 与 DDL

- 全部同类物理表保持字段、索引、字符集、排序规则和 SQL Mode 一致。
- DDL 由 Flyway、Liquibase 或独立部署系统执行，LavShard v0.x 不路由 DDL。
- DDL 采用可回滚或向前兼容的分阶段发布流程。
- 应提供 Schema 指纹或巡检工具，发现物理表漂移。
- 增删索引前评估所有分片的锁、磁盘和执行时间。
- 数据库变更必须先在代表性数据量的分片验证。

## 11. 数据迁移与扩容

扩容不是配置文件中增加一个数据源。标准流程至少包括：

1. 创建并校验新物理节点。
2. 生成新拓扑版本和待迁移桶集合。
3. 全量复制逻辑桶数据。
4. 捕获或短暂停止增量写入并追平差异。
5. 校验行数、校验和及关键业务数据。
6. 原子切换拓扑版本。
7. 观察后清理旧副本，并保留回滚窗口。

迁移期间不得让同一个写请求根据不确定版本随机访问新旧节点。

## 12. 备份、恢复与一致性

- 备份计划必须覆盖全部物理数据库，不能只验证单个节点。
- 跨分片一致性快照需要数据库或备份系统能力；LavShard 不提供全局快照事务。
- 恢复演练必须验证规则版本和拓扑版本与数据备份匹配。
- 配置、规则快照和拓扑映射属于必须备份的元数据。
- 应定期执行桶分布、重复唯一键、孤儿记录和 Schema 漂移检查。

## 13. 上线评审清单

- [ ] 分片键满足非空、不可变、高基数和查询可得。
- [ ] 已评估最大租户和热点键。
- [ ] 已定义全局 ID 与唯一性策略。
- [ ] 关联表满足同桶布局，或已移除跨分片 JOIN/外键依赖。
- [ ] 核心在线查询均能得到单路由。
- [ ] 后台搜索、报表和归档有独立方案。
- [ ] `bucketCount`、`hashVersion`、规则版本和拓扑版本已记录。
- [ ] 所有物理表 Schema 一致。
- [ ] 已定义备份、恢复、扩容和回滚流程。
- [ ] 已通过真实 MySQL 数据量和并发测试。
